# RSS Rule Manager 设计文档

## 1. 目标与范围

本项目实现一个由 Nginx 托管的纯静态管理页面，通过同源反向代理调用 qBittorrent Web API，完成 RSS 下载规则的登录、读取、展示、授权编辑、互斥生成和差量同步。

第一版只管理名称以 `RRM:` 开头的规则。所有非 `RRM:` 规则均为只读数据，同步时不得修改或删除。

MVP 包含：

- 检测登录状态并登录 qBittorrent。
- 读取和展示全部 RSS Rule 的统计信息。
- 解析、展示、新增、修改和删除特殊授权。
- 自动维护 Pure 基准规则和压制组互斥条件。
- 将浏览器内草稿差量同步到 qBittorrent。
- 在同步异常后重新读取服务端真实状态。

MVP 不包含后端服务、数据库、动态维护 Select 选项、多用户权限和跨设备草稿同步。

## 2. 技术架构

项目使用原生 HTML、CSS 和 JavaScript ES Modules，不引入前端框架或运行时依赖。

文件职责：

- `frontend/index.html`：登录界面和管理界面的语义化结构。
- `frontend/css/style.css`：桌面端和移动端响应式样式。
- `frontend/js/config.js`：规则前缀、基准规则名称和固定 Select 选项。
- `frontend/js/api.js`：qBittorrent 登录、规则读取、规则写入和规则删除请求。
- `frontend/js/rule-parser.js`：识别受管规则并还原特殊授权业务模型。
- `frontend/js/rule-generator.js`：生成规则名称、匹配正则、互斥条件和 qBittorrent Rule Definition。
- `frontend/js/sync-planner.js`：比较服务端状态和浏览器草稿，生成有序同步操作。
- `frontend/js/app.js`：页面状态、表单交互、渲染、未保存提示和同步编排。
- `tests/*.test.js`：使用 Node.js 内置 `node:test` 验证纯逻辑和 API 请求契约。

Nginx 托管 `frontend/` 静态文件，并将同源 `/api/v2/` 反向代理到 qBittorrent。浏览器不直接跨域访问 qBittorrent。

## 3. 规则所有权与业务模型

### 3.1 规则命名空间

- 受管规则前缀：`RRM:`。
- Pure 基准规则固定名称：`RRM:Pure@HDSWEB`。
- 特殊授权规则名称：`RRM:授权:<剧集>:<压制组>:<编码>:<分辨率>`。
- 规则名称中的每个业务字段使用 `encodeURIComponent` 编码，解析时使用 `decodeURIComponent` 解码。

无法按上述格式解析的 `RRM:` 特殊授权规则视为受管异常数据。页面显示明确警告，同步功能保持禁用，避免覆盖无法理解的数据。

### 3.2 特殊授权模型

每条授权包含：

```js
{
  series: "九门",
  releaseGroup: "HDSWEB",
  codec: "H265",
  resolution: "1080p"
}
```

同一剧集名称在规范化后只能存在一条授权。规范化规则为去除首尾空白；剧集名称匹配保持大小写不敏感，与 qBittorrent 正则行为一致。

固定 Select 选项：

- 压制组：`HDSWEB`、`HHWEB`。
- 编码：`H264`、`H265`。
- 分辨率：`720p`、`1080p`、`2160p`。

后续需要扩展时直接修改 `frontend/js/config.js`，MVP 不提供页面配置入口。

## 4. 规则生成

### 4.1 Pure 基准规则

`RRM:Pure@HDSWEB` 由本工具管理，并且必须在首次使用前由用户建立或迁移。用户需停用或删除原有不受管的 Pure 全量下载规则，防止两个基准规则同时命中。

基准规则：

- 使用正则匹配 `H265-Pure.HDSWEB`，其中正则元字符按字面量转义。
- `mustNotContain` 是所有已授权剧集名称组成的正则或表达式。
- 保留服务端基准规则的 `affectedFeeds`，特殊授权规则继承相同的 `affectedFeeds`。
- 保留与本工具无关且不影响匹配语义的 qBittorrent Rule Definition 字段。
- 基准规则缺失或 `affectedFeeds` 为空时，页面允许查看和编辑草稿，但禁止同步。

### 4.2 特殊授权规则

每条授权生成一条独立规则。`mustContain` 使用正向预查，要求条目标题同时包含剧集、压制组、编码和分辨率，所有用户数据在写入正则前必须转义。

特殊授权规则的 `mustNotContain` 包含所有授权给其他压制组的剧集。虽然独立规则已通过 `mustContain` 限定目标剧集，仍显式生成跨压制组排除项，以保持规则语义清晰并满足互斥要求。

生成的规则启用正则匹配，并继承 Pure 基准规则的 `affectedFeeds`。与下载目录、保存路径或智能剧集过滤有关的额外字段使用 qBittorrent 的安全默认值；本 MVP 不提供对应编辑入口。

### 4.3 互斥保证

互斥由三层约束共同保证：

1. 表单层拒绝重复剧集授权。
2. Pure 基准规则排除所有特殊授权剧集。
3. 特殊规则排除授权给其他压制组的剧集。

## 5. 登录与 API

页面加载后调用 `GET /api/v2/rss/rules`：

- 成功时进入管理页面。
- 返回 HTTP `401` 或 `403` 时显示登录表单。
- 其他错误显示网络或服务错误，不误判为未登录。

登录使用 `POST /api/v2/auth/login`，请求体为 URL 编码表单，包含 `username` 和 `password`。所有 API 请求均设置 `credentials: "include"`，用户名和密码不写入浏览器存储。

规则 API：

- 读取：`GET /api/v2/rss/rules`。
- 写入：`POST /api/v2/rss/setRule`，表单包含 `ruleName` 和 JSON 序列化的 `ruleDef`。
- 删除：`POST /api/v2/rss/removeRule`，表单包含 `ruleName`。

API 模块将 HTTP 错误、qBittorrent 文本错误和网络错误转换为带操作上下文的异常，供页面展示。

## 6. 页面交互

管理页面包含：

- 顶部栏：应用名称、登录状态和重新登录入口。
- 概览卡片：全部 RSS Rule 数量、RRM 授权数和最后同步时间。
- 基准规则状态：是否存在、绑定订阅源数量和同步阻塞原因。
- 授权列表：剧集、压制组、编码、分辨率、编辑和删除操作。
- 主操作区：新增授权、重新读取、同步到 qBittorrent。

新增和编辑使用模态表单。删除前进行二次确认。所有编辑先写入浏览器内存草稿，只有点击“同步到 qBittorrent”才调用写接口。

页面存在未同步草稿时显示醒目标记，并通过 `beforeunload` 提示用户。同步期间禁用编辑、刷新和重复提交。窄屏下授权表格转换为卡片布局。

## 7. 差量同步

同步前执行完整校验：

- 剧集名称非空。
- 同一剧集没有重复授权。
- Select 值属于固定配置。
- 所有现有 `RRM:` 授权规则均可解析。
- `RRM:Pure@HDSWEB` 存在且至少绑定一个 RSS 源。

页面显示本次新增、更新和删除的规则数量，用户确认后执行。

qBittorrent RSS API 不提供批量事务。为优先避免重复下载，同步操作按以下顺序执行：

1. 删除已取消或字段发生变化的旧授权规则。
2. 写入带最终排除列表的 Pure 基准规则。
3. 写入新增或更新后的特殊授权规则。
4. 重新调用 `GET /api/v2/rss/rules`，以服务端真实状态刷新页面。

任一步骤失败时立即停止后续写操作，显示失败步骤和服务端信息，然后尝试重新读取全部规则。页面不得假装批量操作已回滚或成功。该顺序允许同步过程中出现短暂漏匹配，但避免同一剧集被多个规则同时下载。

删除操作只针对当前服务端存在、名称以 `RRM:` 开头、且能够被本工具识别为特殊授权的规则。基准规则不会因草稿变化被删除，非 `RRM:` 规则永远不进入删除计划。

## 8. 错误处理

- 登录失败：保留登录表单并显示 qBittorrent 返回信息。
- 登录过期：重新显示登录表单，不丢弃当前服务端重新读取前的错误说明。
- 基准规则缺失或未绑定订阅源：禁用同步并给出修复说明。
- 受管规则格式异常：显示规则名称，禁用同步，不自动覆盖。
- 网络中断：显示具体失败操作，允许重新读取。
- 部分同步失败：重新读取实际规则并重新构建草稿，避免继续基于过期状态编辑。
- 正则特殊字符：所有业务字段统一经过正则转义函数处理。

## 9. 测试与验收

使用 Node.js 内置 `node:test`，不增加测试框架依赖。测试采用 ES Modules，并通过依赖注入替换 `fetch` 验证 API 请求。

自动化测试覆盖：

- 授权规则名称的编码、解码和非法格式识别。
- 中文、空格及正则特殊字符的转义。
- Pure 匹配表达式和完整排除列表。
- 特殊授权的四字段匹配及跨压制组排除列表。
- 重复剧集、空剧集和非法 Select 值。
- 基准规则缺失、无 `affectedFeeds` 和异常受管规则。
- 新增、修改、删除的差量计算与操作顺序。
- 非 `RRM:` 规则不会进入更新或删除计划。
- API 的 URL、HTTP 方法、表单参数和 `credentials: "include"`。
- HTTP 未认证、业务错误和网络错误映射。

浏览器冒烟验证覆盖：

- 未登录时显示登录页，登录后加载管理页。
- 新增、编辑、删除草稿及未同步提示。
- 桌面表格和移动端卡片布局。
- 缺失基准规则时同步按钮禁用。
- 同步确认、进行中状态、成功刷新和失败刷新。

验收必须满足：

1. 非 `RRM:` 规则在任何同步路径下保持不变。
2. 同一剧集只能授权一个压制组。
3. Pure 规则自动排除全部特殊授权剧集。
4. 特殊规则包含剧集、压制组、编码和分辨率条件。
5. 修改或删除授权后能生成正确差量。
6. 失败后页面反映 qBittorrent 的实际状态，不显示虚假成功。

## 10. 部署约束

Nginx 必须同时提供静态文件和 qBittorrent API 的同源代理。代理需允许 Cookie 往返，且不重写 `/api/v2/` 下的路径语义。生产环境建议使用 HTTPS，并限制管理页面的网络访问范围。
